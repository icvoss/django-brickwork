- **Catalogue information architecture and a new catalogue manifest**
  (interface-system delivery plan, W0.2, plan decision D8).
  `docs/CATALOGUE.md` documents the family/archetype matrix, the starting
  journey (choose a family, choose an archetype, apply your brand, copy or
  extend, connect Django behaviour), and the owner ruling that family is a
  catalogue taxonomy noun only, never a package API identifier (O1). A new
  `catalogue-manifest.json`, generated by
  `scripts/generate_catalogue_manifest.py`, records family, kind, usage and
  doc pointers for every shipped shell, component, section and archetype
  (5 shells, 40 components, 26 sections, 16 archetypes, including W0.4's
  `bw_theme_switch`). It ships as a
  sibling of `template-manifest.json`, never merged into it: catalogue
  taxonomy is descriptive metadata, not a BR-BW-VER-001 semver contract, and
  is free to evolve in minors. The shipped JSON is the public contract; a
  consumer reads it directly off the installed package (the same pattern
  brickworkui.com's own gallery already uses for `template-manifest.json`),
  and this repo's own in-package reader
  (`brickwork.services._catalogue_manifest`) is deliberately internal, so no
  Python identifier carries "family" as public API. Two scoping decisions
  are recorded in `docs/CATALOGUE.md`: the manifest deliberately carries no
  render-input data (most archetypes need a bound Django form or resolved
  nav tree, neither of which is honestly JSON-representable) and no
  per-family planned/wave status (that is roadmap truth read from
  `ROADMAP.md`, not package truth this manifest can regenerate and
  drift-test).
