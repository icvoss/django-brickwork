- **`{% bw_theme_switch %}` no longer shifts the page when it reveals**
  (icvoss/django-brickwork#272, sev high). The control's root shipped with
  the `hidden` attribute unconditionally, collapsing it to zero footprint
  until `bwThemeSwitch`'s init script revealed it roughly 125ms after first
  paint; every consumer composing the control into a visible header
  inherited the resulting layout shift, measured at CLS 0.16 to 0.19 on a
  consumer's highest-traffic pages. The root now ships with a
  `bw-theme-switch--pre-init` class (`visibility: hidden`, kept in normal
  flow) instead, so the control's real, label-dependent box is reserved from
  first paint; init swaps the class off, changing appearance only, never
  geometry, so the reveal produces no measurable layout shift. Both
  `layout="inline"` and `layout="compact"` share the fix, since both share
  the same root markup. **Behaviour change for existing consumers**: a
  no-JS visitor now gets an invisible reserved box in the header instead of
  no box at all, so a header's total height is no longer zero for the
  control before JS runs; the control itself is still inert and outside the
  accessibility tree without JS, matching the existing no-JS floor (#117).
  **Breaking for consumers whose CSS or tests select the pre-init state by
  the `hidden` attribute**: that attribute is gone, so a selector such as
  `:has([data-bw-theme-switch][hidden])` silently stops matching. The two
  signals are mutually exclusive rather than a preference: `hidden` means
  `display: none`, which is the zero-footprint reveal being fixed here, so
  an attribute-keyed pre-init state cannot reserve a box. The
  `data-bw-theme-switch` hook is unchanged, so the migration is to swap the
  `[hidden]` half for `.bw-theme-switch--pre-init`, giving
  `:has([data-bw-theme-switch].bw-theme-switch--pre-init)`.
  **Also fixed in the same change**: `visibility: hidden` keeps the control's
  descendants at their real geometry (unlike the old `[hidden]` attribute,
  which collapsed them to zero size), which exposed a pre-existing gap in
  `.bw-theme-switch__input`'s own tap-target size, previously masked because
  the raw radios were always 0x0 until JS revealed them. The plain radio now
  carries a 24x24 minimum box (sizing only, no chrome change: the control
  stays deliberately unstyled beyond native fieldset-of-radios), matching the
  WCAG 2.5.8 AA floor every other interactive control in this package already
  meets.
