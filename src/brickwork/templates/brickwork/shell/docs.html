Neither is a WCAG 2.2 AA conformance failure on its own (the a11y gate runs axe with WCAG tags only, so it will not fail you for it), and a docs surface with genuinely no section rail, no page footer, or no site chrome at all is a real case, which is why every one of these is permitted rather than gated. But a consumer removing or adding one owns what the change means for navigation and disclosure: navigation still reachable some other way, and any footer information still presented somewhere a screen-reader user can find. Remove docs_nav_region/docs_footer_region because the region does not exist on your site, never merely to restyle it, which is what overriding the region non-empty is for. Declined regions (ADR-091 decision 2, reasons stated rather than deferred silently): a table of contents / in-page navigation is not shipped, since a TOC is generated from rendered heading structure, a content-pipeline concern this package does not own; a version region is not shipped, since version switching is application routing the package cannot know the shape of (docs_header_region is the home for a consumer-authored switcher); a feedback region is not shipped, since a feedback control posts to a consumer endpoint (docs_footer_region is its home). Revisit each when a consumer has built one and can say what it needed. Source order is normative (ADR-091 decision 3): the article (content) MUST render before the rail (docs_nav_region) in document order. This is the one constraint here purchased with a real consumer defect: brickworkui.com originally rendered its rail first in DOM, putting the article's own

a full screen down on mobile, and its docs index told a reader to "pick a page from the sidebar" above text they had not reached yet (main.css:935-945, page.html:23-32 at 8311fba). `order: -1` in shell.css restores the rail to the visual inline-start at the --bw-breakpoint-lg layout breakpoint, so DOM order and reading order agree at both viewports. A future change reversing this source order is a regression regardless of how the rendered page looks; if a future change ever hides either column at any viewport, the `order` usage must be re-examined rather than preserved (ADR-091 decision 3). Responsive: single breakpoint, at --bw-breakpoint-lg (64rem, the layout breakpoint, chosen over the shell's --bw-breakpoint-md sidebar-collapse token since a 16rem rail plus a readable measure does not fit at 48rem). Below the breakpoint the layout is a single column: the article first, the rail second as a collapsed
disclosure. At and above the breakpoint the layout becomes a persistent two-column grid (16rem minmax(0, 1fr)), the disclosure's summary is hidden (nothing to disclose, the rail is always shown) and its content is revealed regardless of the [open] state by a ::details-content rule in shell.css (icvoss/django-brickwork#451: a closed
