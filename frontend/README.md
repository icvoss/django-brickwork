# brickwork frontend build

This directory holds the build that produces brickwork's shipped static assets.
It runs in **this repo only**, during package development and release, not in
any consumer's Django project.

## What it produces

Into `src/brickwork/static/brickwork/dist/` (committed and shipped in the wheel):

- `tokens.css` : the design-token custom properties (all four axes as scoped
  selectors), vendored from `@bwui/tokens`.
- `tailwind-theme.css` : the `@theme inline` Tailwind bridge mapping `--bw-*`
  tokens to short utility names, vendored from `@bwui/tokens`.
- `tokens.js` : a JS re-export of the token names, vendored from `@bwui/tokens`.
- `token-manifest.json` : the load-bearing brand set (Django-shaped contract,
  including `contrastPairs`; not overwritten by the thinner npm manifest).
- `brickwork.css` : the compiled component/shell CSS, vendored from `@bwui/css`
  and minified with lightningcss, plus the Django `index.css` extras
  (`.bw-icon-directional` and the a11y floor) that `@bwui/css` 0.1.2 omits.
- `brickwork.js` : the compiled Alpine component registrations (wrapping
  `@alpinejs/ui` + `@alpinejs/focus`), which register behaviour and never call
  `Alpine.start()`. Exports `registerBrickworkComponents(Alpine)` (which also
  stamps `data-bw-js-registered` on `<html>` for the shell's DEBUG-only
  forgot-to-register detector, brickwork#87) and the opt-in
  `assertBrickworkRegistered()` hard check.

## The pipeline

`npm run build` runs two stages in order: `build:assets` (`vite build`)
compiles Alpine registration JS from `frontend/src/js/`, then `vendor:bwui`
(`node scripts/vendor-bwui.mjs`) copies published `@bwui/tokens` dist and
minifies `@bwui/css` into `brickwork.css` so a Vite CSS emit cannot overwrite
the npm artefacts (`emptyOutDir: false`). Vite warnings are promoted to hard
errors so broken output cannot ship green. `npm run a11y` drives the
Playwright + axe-core WCAG gate against fixtures generated by
`npm run a11y:fixtures`.

Pip consumers never run this pipeline. Pins live in `package.json`; the
installed versions are recorded in `bwui-pin.json`. See `/LOCKSTEP.md`.

## Decisions already settled (do not relitigate in Phase 0)

Per the build-tool research (2026-07-30, recorded in the umbrella brief):

- **Stable, non-hashed filenames.** Output filenames are fixed
  (`brickwork.css`, not `brickwork-[hash].css`). Versioning rides on the Python
  package's own semver. Consumers reference assets via plain
  `{% static "brickwork/dist/brickwork.css" %}`; their own static storage
  (WhiteNoise / ManifestStaticFilesStorage) handles cache-busting.
- **No `django-vite`.** With stable filenames there is no manifest to resolve,
  so `{% vite_asset %}` has nothing to do that `{% static %}` does not. brickwork
  imposes zero build-tool dependency on consumers.
- **No `django-tailwind` / `django-tailwind-cli`.** Those manage a Tailwind
  build inside a live Django project; brickwork vendors the compiled CSS here.
  A consumer who wants Tailwind utilities still `@import`s `tailwind-theme.css`
  in their own frontend.
- **Alpine + htmx are host-owned peer dependencies.** brickwork bundles neither;
  it registers behaviour onto the host's Alpine instance and never starts it.

The former Phase-0 open questions (token vocabulary, Style Dictionary config,
Vite specifics, brand-authoring mechanism) are all settled and live:
`docs/DESIGN.md` is the canonical token reference and `docs/BRANDING.md` the
brand-override guide. Style Dictionary now runs inside `@bwui/tokens`, not
in this repository's release pipeline.
